# msensor

C++23 sensor driver framework exposed over gRPC (port 50051). Abstract interfaces in `include/msensor/interface/`; in-process pub/sub bus (`Topic`, `Subscription`, `SensorBus`) in `include/msensor/bus/` (target `msensor::bus`, header-only); concrete drivers in `src/<type>/` (lidar, imu, camera, adc, plus sim_* variants); gRPC services in `grpc/` (`msensor::SensorsServer`, built from a `msensor::Sensors{.adc,.camera,.imu,.lidar}` struct plus `ServerOptions`, wires drivers → services); protos in `proto/`. `docs/arch.puml` has the diagram.

## Build / test
- Toolchain lives in the `mdnf1992/cpp-dev` image (devcontainer); OpenCV ≥4.10, jsoncpp, and gRPC are expected there. Presets use `/opt/toolchain/gcc.cmake`.
- Devcontainer (`.devcontainer/devcontainer.json`): image `mdnf1992/cpp-dev`, runs `--privileged` with `/dev` and `/run/udev` mounted, publishes port 50051, and keeps `build/` and `client/.venv` on per-container Docker volumes (so `build/` is not the host's directory). Work, build, and test inside it.
- Configure/build: `cmake --preset gcc && cmake --build --preset build-gcc` (output in `build/gcc`, Ninja). CI (arm64 runner, in the `mdnf1992/cpp-dev` container) runs the same presets plus `ctest --preset test-gcc`.
- Tests (GTest, `test/src/`): `ctest --preset test-gcc` (or `ctest --test-dir build/gcc`), or one test: `build/gcc/test/test_recorder --gtest_filter=Suite.Name`. Tests are only added when msensor is the top-level project.
- `test/draft.cc` (`draft` target) is a scratch executable, not a test.
- `test/bench_msensor.cc` (`bench_msensor` target) is a benchmark, not registered with CTest: `bench_msensor [--passes N] [--only SUBSTR] [--tmp DIR] <recording.pbscan>...` times msensor<->protobuf conversions, `ScanPlayer` parsing, unpaced `RecordingSensorDriver` playback, `ScanRecorder`, and gRPC scan/IMU round trips. Each `ROW` prints its best time and a checksum of its output, so two builds can be compared for equivalence as well as speed. Real recordings live in mslam (`test/data/*.pbscan`); copy the file to compare into an old checkout's `test/` to A/B it.
- Sanitizers (in the image): presets `asan`/`build-asan`/`test-asan` (GCC, `build/asan`) and `tsan`/`build-tsan`/`test-tsan` (clang-21, `build/tsan`), all RelWithDebInfo. `test-asan` sets `ASAN_OPTIONS=detect_container_overflow=0`, because protobuf's `RepeatedField` container annotations misfire with the uninstrumented `libprotobuf.a`. TSan uses clang, not GCC, because on BTI-capable hosts (e.g. Apple silicon) GCC's TSan dies with SIGILL in glibc's `__sigsetjmp` as soon as a thread blocks on a condition variable. `test-tsan` excludes the real-gRPC tests (`test_client_server`) and `CameraConversion.ConcurrentEncodesKeepTheirOwnImages`: gRPC and OpenCV are not instrumented, so their reports are false positives.
- Submodules in `third_party/` (rplidar_sdk, Livox-SDK2) must be initialized: `git submodule update --init`.
- Format: configure with `-DFORMAT_CODE=ON`; the `format` target runs `clang-format -i` on sources as part of `ALL` (it rewrites files on build).

## Gotchas
- Hardware drivers (ads1115, icm-20948, rplidar, mid360, opencv camera) need real devices; use `sim_publisher` and `sim_*` drivers for local runs; `sensor_publisher config/sim_config.json` is the equivalent.
- `sensor_publisher` is config-driven: one JSON config (default `/usr/local/etc/publisher_config.json`, or the one positional CLI arg, plus optional `--record <file>`; template `config/publisher_config.json`; keys in `README.md`) and `msensor::makeSensors()` (`src/factory/`) builds the drivers. A `sim.{lidar,imu,camera,adc}` flag swaps in the simulated driver, so `sensor_publisher config/sim_config.json` runs locally without hardware (`sim_publisher` is the same with all four set). Config/driver errors print one line and exit 1. `sim_publisher`, `remote_recorder` (records over gRPC; the in-process recorder is `BusRecorder`), `playback_publisher` and `scan_checker` are the other apps; the old per-sensor `*_publisher` apps are gone.
- Recordings (`.pbscan`): each entry is a native-endian `uint64` byte count followed by a serialized `sensors::RecordingEntry`. `ScanRecorder` appends and flushes one entry per `record()`; `ScanPlayer` mmaps and parses the file. mslam's test recordings use this format, so keep it (and `proto/`) stable.
- Legacy names: C++ names live in namespace `msensor` (timing is `msensor::timing`); headers also export the old global spellings unless `MSENSOR_NO_LEGACY_NAMES` is defined (msensor's own targets define it per directory; `test/legacy/` does not). Real library targets are `msensor_*` with `msensor::*` aliases; the old bare target names (`timing`, `file`, `IImu`, `msensor_conversions`, ...) are aliases from `cmake/msensor_legacy_targets.cmake`, controlled by `MSENSOR_LEGACY_TARGET_NAMES` (default ON). Only use `msensor::` names inside this repo.
- Library code logs through `msensor::log` (`include/msensor/log/log.hh`, header-only, carried by `msensor::interface`), never `std::cout`/`std::cerr`/`printf`; threshold from `MSENSOR_LOG_LEVEL` (`debug|info|warn|error|off`, default `info`), or `msensor::log::setLevel`/`setSink`. Apps in `src/apps/` print directly.
- `SensorsServer::start()` throws if the listen address cannot be bound; `wait()` blocks until `stop()`. The publishers instead call `msensor::waitForShutdownSignal()` (`grpc/shutdown_signal.hh`) and stop on SIGINT/SIGTERM. Driver sampling loops use `msensor::SamplingThread` (`include/msensor/interface/SamplingThread.hh`).
- `playback_publisher` replays a `.pbscan` recording as a sensor source over gRPC: `playback_publisher -f <file> -s <speed> [-p <port>] [--autoplay]` (`speed` 1.0 = real time, 0 = max; default port 50051). It starts paused unless `--autoplay` is passed; Space toggles playback, `r` rewinds and pauses, Right Arrow doubles speed, Left Arrow halves it (0.125x minimum; from unpaced `0`, it selects 64x), and Ctrl-C exits. It stays running at EOF and can replay through the existing sensor streams. It is backed by `msensor::RecordingSensorDriver` (`src/recorder/`), a push-based LiDAR+IMU source.
- Sensor bus: each driver's single `setXCallback` consumer is a `msensor::Topic<T>` (`include/msensor/bus/topic.hh`), attached only while it has subscribers (a driver with no consumer keeps its no-consumer behaviour). `publish()` runs on the driver's thread and only wraps the sample in `shared_ptr<const T>` and pushes it into each `Subscription`'s bounded FIFO (drop oldest, counted); wake-up hooks run on one dispatcher thread per topic (started with the first subscriber, joined with the last), never on the driver's thread. Destroying a `Subscription` waits out a running hook, so a hook must not destroy a subscription of its own topic. `SensorBus` (`sensor_bus.hh`) owns the drivers and one topic each for lidar/imu/camera (the ADC is pull-based, not on the bus); never call `setXCallback` yourself on a driver that is on a bus. `SensorsServer(Sensors, ServerOptions)` and the positional constructor build a private bus; `SensorsServer(ServerOptions, std::shared_ptr<SensorBus>)` shares one.
- Stream queues: `SensorStreamReactor` (`grpc/sensor_stream.hh`) is a bus subscriber; its subscription is the bounded FIFO of one client, sized by `max_queued_samples` in `ImuStreamRequest`/`LidarStreamRequest`/`CameraStreamRequest` (0 = default; above the cap = cap, logged once). Several clients per stream are served, up to `ServerOptions::max_clients_per_stream` (default 8; one more gets `RESOURCE_EXHAUSTED`, counted by `ClientLimit`). Conversion to protobuf and `StartWrite` run on the dispatcher thread or in `OnWriteDone`, never on the driver's thread. Full queue drops the oldest sample; drops are logged at most once per second per stream and client (warn), plus the total at stream end. Defaults/caps (`kImuQueueLimits` 200/4000, `kLidarQueueLimits` 1/64, `kCameraQueueLimits` 1/8) and `resolveQueueSize()` are in `sensor_stream.hh`. Clients detect loss by gaps in `header.sequence_number`. `SensorsRemoteClient` takes `RemoteClientOptions{scan_queue_size, imu_queue_size}` as an optional second argument. Do not touch `recording.proto` for this.
- Recording on the sensor host: `msensor::BusRecorder` (`include/msensor/recorder/bus_recorder.hh`, `src/recorder/`, target `msensor::bus_recorder`, deliberately not part of `scan_recorder`, which mslam links without the bus) subscribes to the bus's LiDAR and IMU topics (either may be missing) with deep queues (`BusRecorderOptions`, default 256 scans / 8192 IMU samples, not bound by the gRPC caps) and writes through `ScanRecorder` on one writer thread; the `.pbscan` format is unchanged. The topics' wake-up hooks only notify the writer and log drops (warn, at most once per second per stream). Each writer pass snapshots the queue sizes (scans first, then IMU) and writes the IMU samples before the scans. `stop()` joins the writer after a last drain, reads the drop counts, destroys the subscriptions and closes the file; call it before the bus/drivers go away (`sensor_publisher` does: server stop, recorder stop, then the bus is destroyed). `sensor_publisher` builds one `SensorBus` shared by the server and the recorder; it records when `config.recording.enable` (keys `enable`, `file`, `scan_queue`, `imu_queue`; `Config::recording`) or `--record <file>` is given.
- Client loss counting: `SensorsRemoteClient::lostScans()` / `lostImuSamples()` count gaps in `header.sequence_number` per stream with `SequenceGapCounter` (`grpc/sequence_gap_counter.hh`): forward jump `n > 1` counts `n - 1` (modulo 2^32; jumps of 2^31 or more are read as restarts), a backward jump or repeat is a restart, the first number after a (re)connect is ignored. The count happens on the reader thread before the callback and does not alter delivery (mslam depends on it). `remote_recorder` prints the totals on exit.
- Tests that need real gRPC (port-fixed, so not parallel-safe with themselves) are in suite `SensorsServerTest`/`TestClientServer`/`ClientServerContent`, which `test-tsan` excludes by name; put any new gRPC test in one of those suites. If an incremental sanitizer build seems to miss a just-edited test file (the repo is on a synced mount whose mtimes can lag), delete that test's `.o` under `build/<preset>` and rebuild.
- Python client (`client/`, uses `uv`): generated code in `client/proto_gen/` must be regenerated after `.proto` changes with the `grpc_tools.protoc` command in `client/README.md` (the second `robot.proto` command there is stale; no such file here).

## Deployment (`deployment/`)
- Files: `Dockerfile`, `docker-compose.yml`, `entrypoint.sh`, `readme.md`, `config/` (`publisher_config.json`, `mid360_config.json`, mounted at `/config`). Nothing references a `docker/` directory any more.
- `Dockerfile` is multi-stage: build in `mdnf1992/cpp-dev` (`cmake --preset gcc` Release, `--target install` into `/app`, tests off), run on `debian:sid-slim`. It copies `/app` to `/usr/local/`, plus `/usr/local/share` and the hardcoded `/usr/local/lib/aarch64-linux-gnu/` from the build stage, and `deployment/entrypoint.sh` to `/usr/local/bin/`. Build from the repo root as context (compose uses `context: ..`); arm64 via `--platform linux/arm64`.
- The runtime stage is sid so its `libstdc++6` matches the gcc-16 toolchain (trixie's is too old: `GLIBCXX_3.4.35 not found`). Don't copy libstdc++ from the build stage.
- `entrypoint.sh` with no args only prints usage; with args it `exec`s them.
- Compose has two services: `ptp-master` (inline `debian:trixie-slim` image running `ptpd` as grandmaster on `eth0`, host network) and `msensor` (image `mdnf1992/msensor`, `command: ["sensor_publisher", "/config/publisher_config.json"]`, host network, privileged, mounts `./config`, `/dev` and `/run/udev`).
